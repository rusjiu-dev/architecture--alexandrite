# Проект внедрения трейсинга для системы «Александрит»

## Мотивация
Почему в систему нужно добавить трейсинг

Текущая ситуация в системе «Александрит» характеризуется следующими проблемами, которые трейсинг поможет решить:

- **Потеря видимости бизнес-процессов:**
  Заказ проходит через три независимых приложения (онлайн-магазин, CRM, MES), обменивающихся сообщениями через RabbitMQ. При возникновении проблемы команда не может определить, на каком именно сервисе и в какой момент произошёл сбой. Трейсинг обеспечивает сквозную прослеживаемость всего пути заказа.

- **Длительное время диагностики инцидентов:**
  При жалобе клиента или партнёра на «зависший» заказ поддержка вынуждена вручную проверять логи каждого сервиса, сопоставляя их по времени и идентификаторам. Трейсинг сокращает время поиска причины с часов до минут.

- **Сложность выявления узких мест:**
  Распределённая архитектура с асинхронным взаимодействием делает неочевидным, какой компонент является узким местом. Трейсинг визуализирует всё время обработки заказа и позволяет видеть долю каждого компонента в общей задержке.

- **Рост сложности системы:**
  После открытия API и планируемых изменений (асинхронный расчёт стоимости, масштабирование) количество компонентов и связей увеличится. Без трейсинга расследование инцидентов станет практически невозможным.

## Метрики, на которые повлияет внедрение трейсинга

### Технические метрики

| Метрика | Текущее состояние (оценка) | Целевое значение | Влияние трейсинга |
| :--- | :--- | :--- | :--- |
| Mean Time to Detect (MTTD) | Часы (от жалобы клиента) | < 5 минут | Автоматическое обнаружение аномалий по трейсам |
| Mean Time to Resolve (MTTR) | Часы-дни (ручная диагностика) | < 30 минут | Быстрая локализация проблемного сервиса |
| Доля потерянных сообщений | Неизвестно | < 0.01% | Выявление расхождений через сравнение отправленных и полученных спанов |
| Время обработки заказа (end-to-end) | Неизвестно | Измерено, установлен baseline | Инструментальное измерение полного цикла |

### Бизнес-метрики

| Метрика | Текущее состояние | Целевое значение | Влияние трейсинга |
| :--- | :--- | :--- | :--- |
| Время от SUBMITTED до PRICE_CALCULATED | 2-30 минут (оценка по описанию) | Мониторится, P95 < 10 мин | Автоматический алертинг при превышении |
| Доля заказов в «непонятном состоянии» | Высокая (по жалобам) | < 1% | Выявление всех зависших заказов в реальном времени |
| Удовлетворённость B2B-партнёров | Низкая (потеря контрактов) | Стабилизация | Прозрачность обработки запросов для партнёров |

## Компоненты, требующие покрытия трейсингом

На основе анализа C4-диаграммы и потока заказа выделены критические участки, где заказ может быть потерян или «зависнуть»:

### Точки потенциальных сбоев

1. **Internet Shop → Shop API (HTTP)**
   - Сбой: запрос на создание заказа обрывается, Shop API не получает данные.
   - Симптом: заказ остаётся в статусе INITIATED.

2. **Shop API → Shop DB (SQL)**
   - Сбой: транзакция сохранения заказа не завершается.
   - Симптом: заказ создан, но данные неполные.

3. **Shop API → 3D Files Storage (S3 API)**
   - Сбой: файл не загружен, но заказ создан.
   - Симптом: MES не может рассчитать стоимость без файла.

4. **CRM API → RabbitMQ (AMQP)**
   - Сбой: сообщение о подтверждении заказа не отправлено.
   - Симптом: заказ «зависает» между CRM и MES.

5. **Shop API → RabbitMQ (AMQP)**
   - Сбой: сообщение о новом заказе потеряно.
   - Симптом: заказ не попадает в MES для расчёта.

6. **MES API → RabbitMQ (AMQP, consumption)**
   - Сбой: consumer не обрабатывает сообщение, оно уходит в DLX.
   - Симптом: заказ не рассчитывается, статус не меняется.

7. **MES API → MES DB (SQL)**
   - Сбой: результат расчёта не сохранён.
   - Симптом: статус PRICE_CALCULATED не проставляется.

8. **MES API → 3D Files Storage (S3 API)**
   - Сбой: файл не может быть прочитан.
   - Симптом: расчёт невозможен, процесс останавливается.

9. **CRM API → CRM Frontend (HTTP)**
   - Сбой: интерфейс не отображает актуальный статус.
   - Симптом: продавец не видит заказ для подтверждения.

10. **MES API → MES Frontend (HTTP)**
    - Сбой: дашборд не обновляется.
    - Симптом: оператор не видит новые заказы.

## Схема покрытия трейсингом (текстовое описание)

На C4-диаграмме контейнеров должны быть отмечены следующие компоненты (выделены красным):

**Новые компоненты:**
- `Trace Collector` (OpenTelemetry Collector) — централизованный сборщик трейсов
- `Trace Storage` (Yandex Managed Service for ClickHouse или self-hosted Grafana Tempo) — хранилище трейсов
- `Trace UI` (Grafana) — интерфейс для анализа трейсов (развёрнут в рамках мониторинга)

**Существующие компоненты, которые инструментируются (отмечены красной обводкой/меткой):**
- `Shop API` (Java Spring Boot) — добавление OpenTelemetry Java Agent
- `CRM API` (Java Spring Boot) — добавление OpenTelemetry Java Agent
- `MES API` (C#) — добавление OpenTelemetry .NET SDK
- `RabbitMQ` — трассировка сообщений через OpenTelemetry messaging instrumentation
- `Shop DB`, `MES DB` — трассировка SQL-запросов (автоматически через агенты)

**Новые связи (красные стрелки):**
- `Shop API → Trace Collector`
- `CRM API → Trace Collector`
- `MES API → Trace Collector`
- `Trace Collector → Trace Storage`
- `Trace UI → Trace Storage` (чтение)

## Предлагаемое решение

### Стек технологий

| Компонент | Технология | Обоснование |
| :--- | :--- | :--- |
| Инструментирование Java (Shop API, CRM API) | OpenTelemetry Java Agent (автоматическая инжекция) | Не требует изменений кода для HTTP, SQL, AMQP. Добавляется JVM-аргументом при запуске. |
| Инструментирование C# (MES API) | OpenTelemetry .NET SDK + библиотеки | Прямое встраивание в код для кастомных спанов бизнес-логики. |
| Экспорт трейсов | OTLP (OpenTelemetry Protocol) | Стандартный протокол для передачи трейсов. |
| Trace Collector | OpenTelemetry Collector (Deployment на EC2) | Принимает данные от агентов, обогащает, фильтрует, отправляет в хранилище. |
| Trace Storage | Grafana Tempo (self-hosted) или Yandex Managed Service for ClickHouse | Tempo интегрирован с Grafana, поддерживает OTLP. ClickHouse — если объём трейсов очень большой. |
| Trace UI | Grafana (уже запланирован в рамках мониторинга) | Единый интерфейс для метрик, логов и трейсов. |

### Данные, попадающие в трейсинг

**Контекст трассировки (обязательные данные):**
- `trace_id` — уникальный идентификатор сквозной цепочки вызовов (соответствует одному заказу от создания до завершения).
- `span_id` — идентификатор отдельной операции внутри цепочки.
- `parent_span_id` — связь с родительской операцией.
- `service.name` — имя сервиса (например, shop-api, mes-api, crm-api).
- `span.name` — название операции (например, POST /api/orders, calculate_price, send_to_rabbitmq).
- `span.kind` — тип спана (CLIENT, SERVER, CONSUMER, PRODUCER).

**Бизнес-атрибуты (кастомные теги):**
- `order.id` — идентификатор заказа (сквозной для всех сервисов).
- `order.status` — текущий статус заказа в момент операции.
- `customer.id` — идентификатор клиента (для B2C) или партнёра (для B2B).
- `source` — источник заказа (b2c_website / b2b_api).
- `file.format` — формат 3D-файла (STL, OBJ, STEP).
- `file.size_bytes` — размер файла.
- `calculation.time_ms` — время расчёта стоимости.
- `calculation.complexity` — сложность модели (количество полигонов).
- `queue.name` — имя очереди RabbitMQ.
- `messaging.operation` — тип операции с сообщением (publish, receive, process).

**Технические атрибуты:**
- `http.method`, `http.url`, `http.status_code` — для HTTP-запросов.
- `db.system`, `db.name`, `db.operation` — для запросов к БД.
- `exception.type`, `exception.message`, `exception.stacktrace` — при ошибках.
- `host.name`, `container.id` — информация об инстансе.

### Как это работает: сценарий трассировки заказа

1. Пользователь нажимает «Сделать заказ» в Internet Shop.
2. Internet Shop отправляет HTTP-запрос к Shop API. В заголовке запроса передаётся `traceparent` (стандарт W3C Trace Context).
3. Shop API (Java Agent) создаёт `SERVER` span с именем `POST /api/orders`.
4. При сохранении в Shop DB автоматически создаётся `CLIENT` span для SQL-запроса.
5. При отправке сообщения в RabbitMQ создаётся `PRODUCER` span. `trace_id` и `span_id` передаются в заголовках AMQP-сообщения.
6. MES API (C# SDK) получает сообщение из очереди. Из заголовков извлекается контекст трассировки. Создаётся `CONSUMER` span, связанный с родительским `PRODUCER` span.
7. MES API создаёт `SERVER` span для расчёта стоимости. Все внутренние операции (чтение файла из S3, запрос к MES DB) создают дочерние `CLIENT` спаны.
8. При отправке сообщения о завершении расчёта создаётся `PRODUCER` span в очередь RabbitMQ.
9. CRM API (Java Agent) получает сообщение и создаёт `CONSUMER` span.
10. Все спаны экспортируются в OpenTelemetry Collector, агрегируются в трейс с одним `trace_id` и сохраняются в Tempo.

## Компромиссы

### Случаи, когда трейсинг не принесёт пользы или невозможен

1. **Трассировка проприетарного MES (если код не был передан полностью)**
   Хотя компания купила исходный код MES, в описании указано, что это готовое решение. Если часть компонентов (например, модуль расчёта стоимости) поставляется в виде скомпилированных библиотек без возможности модификации, встроить кастомные спаны в них будет невозможно. В этом случае инструментирование ограничится автоматическими спанами (HTTP, SQL), а внутренняя логика расчёта останется «чёрным ящиком».

2. **Трассировка на уровне браузера**
   Frontend-приложения (Internet Shop, CRM, MES SPA) являются SPA и выполняются в браузере пользователя. Инструментирование клиентской стороны возможно (OpenTelemetry JS), но:
   - Добавляет накладные расходы на загрузку страницы.
   - Раскрывает внутренние endpoint'ы сбора трейсов (требуется отдельный шлюз).
   - Может конфликтовать с политиками безопасности контента (CSP).
   - **Решение:** На первом этапе ограничиться серверным трейсингом. Контекст трассировки можно передавать от браузера через заголовок запроса, но без клиентских спанов.

3. **Высокая стоимость хранения трейсов при полном сэмплировании**
   При линейном росте заказов (100+ ежемесячно плюс API-трафик) объём трейсов будет расти. Полное сохранение всех трейсов может стать дорогим.
   - **Решение:** Внедрить head-based sampling на коллекторе:
     - Сохранять 100% трейсов для заказов (по атрибуту `order.id`).
     - Для остальных запросов (health checks, статические ресурсы) — 10%.
     - Для B2B API-запросов — 100% (критично для партнёров).

4. **Трассировка синхронных запросов с долгим временем выполнения**
   Расчёт стоимости занимает 2-30 минут. Стандартный HTTP-спан будет висеть всё это время, что приведёт к артефактам в визуализации и может превысить таймауты коллектора.
   - **Решение:** После перехода на асинхронную модель расчёта (инициатива №1 из предыдущего задания) спан HTTP-запроса будет закрываться после помещения задачи в очередь. Процесс расчёта будет создавать отдельный спан, связанный с исходным через `trace_id`.

5. **Зависимость от единой платформы мониторинга**
   Если Grafana или Tempo станут недоступны, команда потеряет не только трейсы, но и метрики. Это создаёт единую точку отказа для observability.
   - **Решение:** Рассмотреть возможность сохранения трейсов также в файловое хранилище (S3) в формате OTLP JSON как резервное копирование.

## Аспекты безопасности

### Аутентификация и авторизация

- **Доступ к Trace UI (Grafana):**
  - Внедрение SSO-аутентификации через корпоративный LDAP или OAuth2-провайдер компании.
  - Ролевая модель: роль `viewer` для разработчиков и QA, роль `editor` для DevOps и тимлида, роль `admin` для DevOps-инженера.
  - Доступ только из внутренней сети компании или через VPN. Внешний доступ запрещён.

- **Доступ к OpenTelemetry Collector:**
  - Коллектор размещается во внутренней сети (VPC), недоступен из интернета.
  - Приём данных только от известных сервисов. Верификация по списку разрешённых IP-адресов или через Mutual TLS (mTLS), если сервисы распределены.

- **Доступ к Trace Storage (Tempo):**
  - Хранилище размещается в изолированной подсети.
  - Доступ на чтение — только от Grafana (service-to-service authentication).
  - Доступ на запись — только от OpenTelemetry Collector.

### Защита данных

- **Фильтрация чувствительных данных:**
  Настройка процессора `attributes` в OpenTelemetry Collector для удаления или хеширования чувствительных данных:
  - `customer.email` → удалить или хешировать (SHA-256).
  - `customer.phone` → удалить.
  - `api_key` → маскировать (оставлять последние 4 символа).
  - `file.path` → удалить, оставить только `file.format` и `file.size_bytes`.

  > **Важно:** Данные кредитных карт или платёжной информации не должны попадать в трейсы ни при каких обстоятельствах.

- **Срок хранения трейсов:**
  - Настроить retention policy в Tempo: 7 дней для полных трейсов, 30 дней для агрегированных данных.
  - Автоматическое удаление данных старше срока хранения.

### Сетевая безопасность

- **Шифрование трафика:**
  - Включить TLS для OTLP-экспорта между агентами и коллектором (даже внутри VPC — defense in depth).
  - Включить TLS для соединения между Grafana и Tempo.

- **Аудит доступа:**
  - Логирование всех запросов к Trace UI с указанием пользователя, времени и поискового запроса.
  - Хранение аудит-логов в отдельном защищённом хранилище.

## Дополнительное задание: Автоматический мониторинг процесса прохождения заказа и алертинг

### Концепция

На основе данных трейсинга строится автоматическая система контроля бизнес-процесса «Жизненный цикл заказа». Система отслеживает полный путь заказа от создания до закрытия и выявляет аномалии в реальном времени.

### Компоненты решения (зелёный цвет на схеме)

**Новые компоненты (выделены зелёным):**
- `Trace Analytics Engine` — сервис на Python/Go, который в реальном времени анализирует трейсы из OpenTelemetry Collector (через OTLP stream) и выявляет аномалии бизнес-процесса.
- `Business Process Alert Rules` — набор правил в формате YAML, определяющих нормальное поведение заказа и триггеры алертов.
- `Alert Manager` — компонент, развёрнутый в рамках мониторинга (Prometheus Alertmanager), который также принимает алерты от Trace Analytics Engine.

### Алгоритм мониторинга процесса заказа

**Шаг 1. Получение трейсов**
Trace Analytics Engine подписывается на OTLP stream от OpenTelemetry Collector и фильтрует трейсы, содержащие атрибут `order.id`.

**Шаг 2. Построение модели процесса**
На основе последовательности спанов в трейсе определяется, какие статусы прошёл заказ и за какое время:

```text
Expected flow:
INITIATED → FILE_UPLOADED → SUBMITTED → PRICE_CALCULATED → 
MANUFACTURING_APPROVED → MANUFACTURING_STARTED → 
MANUFACTURING_COMPLETED → PACKAGING → SHIPPED → CLOSED
```
### Шаг 3. Проверка правил

| Правило | Условие срабатывания | Таймаут | Действие |
| :--- | :--- | :--- | :--- |
| Заказ завис в статусе | Заказ находится в одном статусе дольше порогового времени без перехода | SUBMITTED: 35 мин (30 мин макс. расчёт + запас). MANUFACTURING_APPROVED: 24 часа. MANUFACTURING_STARTED: 48 часов. | Создание алерта с order.id, текущим статусом, временем в статусе |
| Нарушение последовательности статусов | Статусы появляются в неожиданном порядке (например, SHIPPED без PACKAGING) | Мгновенно | Критический алерт, подозрение на потерю сообщений |
| Потерянный заказ | order.id был создан (INITIATED span), но в течение 1 часа нет спана SUBMITTED | 1 час | Предупреждение: возможно, пользователь бросил корзину |
| Долгий расчёт стоимости | Время между CONSUMER span (начало расчёта) и PRODUCER span (отправка результата) > 30 минут | 30 минут | Алерт: возможна слишком сложная модель или проблема с вычислительными ресурсами |
| Заказ не закрыт | Заказ в статусе SHIPPED более 14 дней | 14 дней | Предупреждение: требуется ручная проверка |

### Шаг 4. Отправка алертов

Trace Analytics Engine отправляет алерты в Alertmanager через API. Alertmanager маршрутизирует их согласно настройкам:

- **Критические алерты** (потеря сообщений, зависший заказ > 1 дня) → звонок on-call инженеру.
- **Предупреждения** → Slack-канал #support.
- **Информационные сообщения** → дашборд в Grafana.

### План реализации автоматического мониторинга

1. Разработать Trace Analytics Engine как микросервис.
2. Определить и закодировать правила проверки жизненного цикла заказа.
3. Настроить подписку на OTLP stream от коллектора.
4. Интегрировать с Alertmanager через API.
5. Создать дашборд «Order Lifecycle Health» в Grafana, отображающий:
   - Количество заказов в каждом статусе (реальное время).
   - Среднее время перехода между статусами.
   - Список «зависших» заказов.
   - Тренд количества аномалий по дням.
