# Проект внедрения мониторинга для системы «Александрит»

## Мотивация

Текущая ситуация в компании характеризуется следующими проблемами, которые мониторинг поможет решить:

- **Фактические потери бизнеса:**
  Компания уже потеряла несколько крупных контрактов после открытия API. Жалобы от B2B-клиентов и розничных покупателей на просроченные заказы растут ежемесячно. При этом производственные мощности позволяют обрабатывать заказы — проблема находится в IT-системах.

- **Отсутствие объективных данных для принятия решений:**
  Яндекс Метрика покрывает только пользовательское поведение на сайте онлайн-магазина. После открытия API значительная часть бизнес-транзакций проходит вне зоны видимости этой метрики. Команда не имеет данных о том, что происходит в MES, CRM, очередях сообщений и базах данных.

- **Реактивный подход к инцидентам:**
  О проблемах команда узнаёт от пользователей (продавцов, операторов, B2B-клиентов). Это означает, что инциденты обнаруживаются с задержкой в часы или дни, когда негативный эффект уже накоплен. Мониторинг обеспечит проактивное обнаружение проблем.

- **Невозможность объективно оценивать эффект изменений:**
  После реализации инициатив по оптимизации расчёта стоимости, дашборда MES и масштабированию потребуется подтверждение их эффективности. Без baseline-метрик невозможно доказать бизнесу, что вложенные ресурсы принесли результат.

- **Обоснование инвестиций для бизнеса:**
  Стоимость внедрения мониторинга составляет незначительную долю от потерь, которые компания несёт из-за одного потерянного крупного контракта. Мониторинг позволит обнаруживать деградацию сервиса до того, как она приведёт к срыву SLA перед партнёрами, и сократит время восстановления сервиса с часов до минут.

## Выбор подхода к мониторингу

Для разных компонентов системы применяются различные подходы, соответствующие их роли:

- **Для API-сервисов (Shop API, CRM API, MES API) — метод RED:**
  - **Rate (RPS)** — интенсивность запросов
  - **Errors (ошибки)** — доля запросов с ошибками
  - **Duration (латентность)** — время ответа

  **Обоснование:** API являются точкой входа для пользователей и партнёров. Для этих компонентов критично понимать, сколько запросов обслуживается, с каким качеством и насколько быстро. RED напрямую связан с пользовательским опытом и SLA.

- **Для инфраструктурных ресурсов (базы данных, очереди, хранилища) — метод USE:**
  - **Utilisation (использование)** — процент занятости ресурса
  - **Saturation (насыщение)** — длина очереди ожидания к ресурсу
  - **Errors (ошибки)** — количество ошибок ресурса

  **Обоснование:** Базы данных и очереди — разделяемые ресурсы. Их перегрузка влияет на все сервисы одновременно. USE позволяет предсказать исчерпание ёмкости до того, как это приведёт к инциденту.

- **Для бизнес-процессов — «Четыре золотых сигнала» с фокусом на трафик и латентность бизнес-операций:**
  - **Трафик:** количество бизнес-транзакций (созданных заказов, запросов на расчёт стоимости)
  - **Ошибки:** доля неуспешных бизнес-операций
  - **Латентность:** время выполнения ключевых бизнес-сценариев (от отправки заказа до получения стоимости)
  - **Сатурация:** глубина очереди необработанных задач

## Метрики для отслеживания

### API-сервисы (RED)

1. **Response time (latency) for shop API, CRM API, MES API**
   - **Зачем:** Измерение пользовательского опыта. Рост латентности — ранний признак деградации. Для MES API критично из-за жалоб на медленную загрузку дашборда.
   - **Ярлыки:** endpoint, method, status_code, percentile (p50, p95, p99). Перцентили необходимы, так как среднее значение скрывает выбросы для медленных запросов.

2. **Number of requests (RPS) for shop API, CRM API, MES API**
   - **Зачем:** Базовый показатель нагрузки. Позволяет коррелировать рост ошибок с пиками трафика, прогнозировать потребность в масштабировании.
   - **Ярлыки:** endpoint, method.

3. **Number of HTTP 200, HTTP 500 for shop API, CRM API, MES API**
   - **Зачем:** Количество успешных ответов и ошибок сервера. HTTP 500 — прямые признаки инцидентов, требующих немедленного реагирования.
   - **Ярлыки:** endpoint, error_type. Для HTTP 500 важно различать типы ошибок (timeout, exception, out-of-memory).

4. **Number of requests (RPS) per user for MES API (дополнительно к стандартным)**
   - **Зачем:** Сценарий открытого API для B2B-партнёров создаёт риск, что один партнёр может перегрузить систему. Эта метрика позволяет выявить источник аномальной нагрузки.
   - **Ярлыки:** api_key, partner_name, endpoint.

### Инфраструктура (USE)

5. **CPU % for shop API, CRM API, MES API**
   - **Зачем:** Показатель утилизации вычислительных ресурсов. Постоянно высокий CPU — сигнал к масштабированию. Для MES API критичен, так как расчёт стоимости — CPU-интенсивная операция.
   - **Ярлыки:** instance_id, environment (dev/release/prod).

6. **Memory Utilisation for shop API, CRM API, MES API**
   - **Зачем:** Утечки памяти или нехватка памяти приводят к падению сервисов. Мониторинг тренда позволяет обнаружить проблему до OOM-краша.
   - **Ярлыки:** instance_id, environment.

7. **Memory Utilisation for shop db instance, MES db instance**
   - **Зачем:** Базы данных используют память для кэширования. Недостаток памяти приводит к росту дискового I/O и деградации производительности всех запросов.
   - **Ярлыки:** instance_id, environment, db_name.

8. **Number of connections for shop db instance, MES db instance**
   - **Зачем:** Исчерпание пула соединений — частая причина ошибок. Рост числа соединений коррелирует с ростом нагрузки и может указывать на утечки соединений в коде.
   - **Ярлыки:** instance_id, state (active, idle, waiting).

9. **Size of shop db instance, MES db instance**
   - **Зачем:** Контроль за ростом данных. Неожиданный рост может указывать на проблемы (например, отсутствие очистки логов) или требовать планового увеличения дискового пространства.
   - **Ярлыки:** db_name, environment.

### Очередь сообщений (USE + бизнес-сигналы)

10. **Number of message in flight in RabbitMQ**
    - **Зачем:** Показатель текущей загрузки обработчиков. Рост количества сообщений в полёте — признак того, что consumer'ы не справляются с нагрузкой. Критично для очереди расчёта стоимости.
    - **Ярлыки:** queue_name, vhost.

11. **Number of dead-letter-exchange letters in RabbitMQ**
    - **Зачем:** Сообщения в DLX — это потерянные бизнес-операции (необработанные заказы, непереданные статусы). Каждое такое сообщение потенциально означает заказ, который «завис».
    - **Ярлыки:** queue_name, vhost, error_reason.

### Дополнительные метрики (не из списка)

12. **Время выполнения расчёта стоимости (business transaction duration)**
    - **Зачем:** Прямая бизнес-метрика. Рост времени расчёта означает, что клиенты и партнёры дольше ждут результата. После оптимизации эта метрика подтвердит эффект изменений.
    - **Ярлыки:** model_complexity_bucket (low/medium/high), source (internal/api).

13. **Количество заказов по статусам (бизнес-метрика)**
    - **Зачем:** Позволяет видеть «заторы» в процессе. Например, рост количества заказов в статусе SUBMITTED без перехода в PRICE_CALCULATED указывает на проблемы с расчётом стоимости.
    - **Ярлыки:** status, source (b2c/b2b).

14. **Saturation для очереди расчёта стоимости — глубина очереди**
    - **Зачем:** Количество задач, ожидающих обработки. Если метрика растёт, время выполнения заказа для клиента увеличивается, даже если API продолжает отвечать.
    - **Ярлыки:** queue_name.

## Показатели насыщенности и пороговые значения

### Для API-сервисов

| Метрика | Порог насыщенности | Обоснование | Действие при превышении |
| :--- | :--- | :--- | :--- |
| P95 latency MES API | > 2 секунд | По описанию, дашборд операторов должен работать быстро. 2 секунды — верхняя граница комфортного взаимодействия. | Автоматическое создание тикета в очереди разработки с приоритетом high. Уведомление в Slack команды. |
| HTTP 500 rate (любой API) | > 1% от RPS | Ошибки сервера недопустимы для API партнёров. 1% — консервативный порог, превышение означает активный инцидент. | Срочное уведомление on-call инженера (звонок/смс), автоматический запуск сбора диагностической информации. |
| RPS per user (MES API) | > 100 RPS от одного партнёра | Предотвращение монополизации ресурсов одним клиентом в ущерб остальным. | Rate limiting с возвратом HTTP 429, уведомление DevOps о необходимости проверки. |

### Для баз данных

| Метрика | Порог насыщенности | Обоснование | Действие при превышении |
| :--- | :--- | :--- | :--- |
| CPU % для БД | > 80% устойчиво более 5 минут | Дальнейший рост приведёт к экспоненциальному увеличению времени запросов и возможному отказу в обслуживании. | Уведомление DevOps. При ручном масштабировании — подготовка к увеличению ресурсов или добавлению реплики. При автоскейлинге — триггер для добавления реплики. |
| Connections utilisation | > 80% от max_connections | Исчерпание пула соединений блокирует все сервисы, обращающиеся к БД. | Уведомление разработчиков и DevOps. Проверка на утечки соединений. При необходимости — ручное или автоматическое увеличение лимита. |
| Disk usage (размер БД) | > 80% выделенного пространства | Исчерпание дискового пространства приводит к полной остановке БД. | Автоматический тикет на расширение диска. Уведомление DevOps с высоким приоритетом. |

### Для очередей сообщений

| Метрика | Порог насыщенности | Обоснование | Действие при превышении |
| :--- | :--- | :--- | :--- |
| Queue depth (расчёт стоимости) | > 100 сообщений | Очередь растёт, когда consumer'ы не справляются. 100 задач в очереди при средней обработке 3 минуты означает задержку до 5 часов для клиента в конце очереди. | Автоматическое масштабирование consumer'ов (если настроено). Уведомление команды о необходимости ручного вмешательства. |
| DLX message count | > 0 | Каждое сообщение в DLX — потерянная или задержанная бизнес-операция. Это не должно происходить в нормальном режиме. | Немедленное уведомление on-call с деталями сообщения. Автоматическое создание инцидента. |

## План действий (драфт технического задания)

### Этап 1. Развёртывание инфраструктуры мониторинга (1 спринт)

1. Создать инстанс time-series базы данных VictoriaMetrics на Yandex Cloud (совместима с Prometheus, эффективнее по памяти чем Thanos для небольших инсталляций).
2. Развернуть Prometheus как систему сбора метрик (отдельный EC2 инстанс или как часть кластера мониторинга).
3. Развернуть Grafana для визуализации (EC2 инстанс или Managed Service for Grafana на Yandex Cloud).
4. Настроить Alertmanager для маршрутизации уведомлений в Slack, email и телефон (sms-шлюз).

### Этап 2. Инструментирование приложений (1-2 спринта)

- **Добавить экспорт метрик в приложения Java (Shop API, CRM API):**
  - Подключить Micrometer + Prometheus registry.
  - Настроить автоматический экспорт HTTP-метрик (RPS, латентность, коды ответов) с ярлыками endpoint и method.
  - Добавить кастомные метрики для бизнес-операций (создание заказа, переходы статусов).

- **Добавить экспорт метрик в MES API (C#):**
  - Подключить библиотеку AppMetrics или Prometheus-net.
  - Настроить экспорт HTTP-метрик.
  - Добавить метрику времени расчёта стоимости с гистограммой.
  - Добавить метрику количества заказов по статусам (gauge).

- **Настроить экспорт метрик RabbitMQ:**
  - Включить плагин `rabbitmq_prometheus`.
  - Настроить сбор метрик очередей: глубина, messages in flight, DLX.

### Этап 3. Инфраструктурный мониторинг (1 спринт)

1. Настроить Node Exporter на всех EC2 инстансах для сбора CPU, памяти, дискового I/O.
2. Настроить сбор метрик Yandex Managed PostgreSQL через встроенный экспортёр или API Yandex Cloud.
3. Настроить сбор метрик S3-хранилища (размер бакета, количество объектов) через API Yandex Cloud.

### Этап 4. Дашборды и алертинг (1 спринт)

- **Создать дашборды в Grafana:**
  - **Обзорный дашборд «Executive Summary»:** RPS, латентность, ошибки по всем API, глубина очереди расчёта стоимости.
  - **Дашборд «MES API Detail»:** детальные метрики RED, время расчёта стоимости, статусы заказов.
  - **Дашборд «Infrastructure»:** CPU, память, соединения БД, размер хранилищ.
  - **Дашборд «RabbitMQ»:** состояние очередей, DLX, throughput.
  - **Дашборд «Business»:** заказы по статусам, время от SUBMITTED до PRICE_CALCULATED.

- **Настроить правила алертинга** в соответствии с таблицей показателей насыщенности.

### Этап 5. Интеграция в процессы (перманентно)

1. Добавить проверку дашбордов в Definition of Done для релизов: перед деплоем на продакшн убедиться, что ключевые метрики не деградировали.
2. Настроить автоматическую привязку алертов к инцидентам в системе управления задачами команды.
3. Провести обучение команды по использованию дашбордов и реагированию на алерты.
