# Проект внедрения логирования для системы «Александрит»

## Мотивация
Почему в систему нужно добавить структурированное логирование

Текущая ситуация в системе «Александрит» характеризуется следующими проблемами, которые структурированное логирование поможет решить:

- **Диагностика «со слов клиента»**:
  Разработчики и поддержка узнают о проблемах от клиентов и партнёров, которые не могут предоставить технические детали. Время на воспроизведение и локализацию проблемы кратно превышает время на её исправление. Структурированные логи обеспечивают проактивный доступ к истории событий.

- **Распределённая архитектура без единого контекста**:
  Заказ проходит через три приложения, каждое пишет логи в своём формате и в своё хранилище (локальные файлы на EC2). При расследовании инцидента приходится вручную собирать логи с разных машин, сопоставляя временные метки. Централизованное логирование с единым форматом решает эту проблему.

- **Рост сложности после изменений**:
  После внедрения асинхронного расчёта стоимости, масштабирования и очередей количество потенциальных точек отказа увеличится. Без централизованных логов расследование станет практически невозможным.

- **Юридическая защита**:
  При потере B2B-контрактов компания должна иметь возможность доказать, что обработка запроса была выполнена корректно и в срок. Логи с временными метками и идентификаторами заказов являются таким доказательством.

## Метрики, на которые повлияет внедрение логирования

### Технические метрики

| Метрика | Текущее состояние (оценка) | Целевое значение | Влияние логирования |
| :--- | :--- | :--- | :--- |
| Mean Time to Resolve (MTTR) | Часы-дни | < 30 минут | Быстрый поиск по correlation ID (order.id) сокращает время локализации |
| Доля инцидентов, решённых без эскалации на разработку | Низкая | > 60% | Поддержка может самостоятельно найти причину по логам |
| Время восстановления данных о сбое | Дни (восстановление со слов) | Мгновенно | Логи сохраняются централизованно и доступны сразу |
| Покрытие логированием критических бизнес-операций | ~0% (только дефолтные логи) | 100% | Явное логирование всех переходов статусов заказа |

### Бизнес-метрики

| Метрика | Текущее состояние | Целевое значение | Влияние логирования |
| :--- | :--- | :--- | :--- |
| Количество жалоб B2B-партнёров | Высокое (ежедневные жалобы) | Снижение на 50% | Быстрое расследование → быстрое решение → меньше эскалаций |
| Удовлетворённость поддержки | Низкая (выгорание от рутины) | Повышение | Снижение времени на расследование на 70% |

## Приоритизация: какие системы покрывать в первую очередь

Команда не может реализовать логирование и трейсинг всех систем единовременно. Приоритет определяется на основе влияния на ключевые бизнес-процессы и частоты инцидентов.

### Приоритет 1: MES API (C#)

**Обоснование:**
- Центральный узел обработки заказов и расчёта стоимости.
- Единственный компонент на C# — наименее знакомая команде технология, требует приоритетного покрытия.
- Здесь происходит расчёт стоимости (самая долгая и проблемная операция).
- Сюда приходят запросы от B2B-партнёров через API — потеря этих логов критична для контрактов.
- Взаимодействует с RabbitMQ, MES DB, S3 — все потенциальные точки сбоя.

### Приоритет 2: CRM API (Java Spring Boot)

**Обоснование:**
- Управляет подтверждением заказов (статус MANUFACTURING_APPROVED).
- Точка входа для продавцов — жалобы клиентов поступают именно сюда.
- Отправляет сообщения в RabbitMQ — потеря сообщения здесь означает «зависший» заказ.
- Java-команда из двух инженеров может реализовать быстрее, чем C# разработчик один.

### Приоритет 3: Shop API (Java Spring Boot)

**Обоснование:**
- Точка создания заказа и загрузки файлов.
- Меньше жалоб, чем на MES и CRM (проблемы проявляются позже в цепочке).
- Может быть покрыт после стабилизации MES и CRM.

## Приоритет для трейсинга (аналогичный порядок)

Трейсинг критичен для:
- MES API — сквозная трассировка расчёта стоимости.
- CRM API — трассировка передачи сообщений в RabbitMQ.
- Shop API — трассировка создания заказа.

**Вывод:** Логирование и трейсинг внедряются одновременно для каждой системы в порядке приоритета: MES API → CRM API → Shop API. Это позволяет сразу получить полную картину (логи + трейсы) для наиболее проблемного компонента.

## Какие логи нужно собирать

### Уровни логирования и обстоятельства использования

| Уровень | Назначение | Когда используется |
| :--- | :--- | :--- |
| ERROR | Ошибки, требующие немедленного внимания. Исключения, падения сервисов, потеря данных. | Все необработанные исключения, ошибки соединения с БД/очередью/S3, критические нарушения бизнес-логики (заказ не может быть обработан). |
| WARN | Предупреждения о потенциально опасных ситуациях, которые не нарушают работу, но могут привести к ошибкам. | Превышение порога времени обработки (но не максимума), повторные попытки отправки сообщений, приближение к лимитам (размер файла, количество заказов от одного клиента). |
| INFO | Ключевые бизнес-события и технические операции. Основной уровень для расследования инцидентов. | Все переходы статусов заказа, создание/завершение заказа, отправка/получение сообщений, начало/завершение расчёта стоимости, запросы к внешним API. |
| DEBUG | Детальная отладочная информация. Включается только на dev-окружении или точечно для расследования. | Полные тела запросов/ответов, детали SQL-запросов, внутреннее состояние объектов. |
| TRACE | Максимально детальная информация. Не используется в продакшене. | Пошаговое выполнение алгоритмов, значения переменных в циклах. |

### Список необходимых логов уровня INFO

#### Для всех сервисов (Shop API, CRM API, MES API)

**HTTP-запросы:**
- Время запроса (timestamp)
- Идентификатор запроса (trace_id, span_id)
- HTTP-метод и URL (http.method, http.url)
- IP-адрес клиента (client.ip)
- Код ответа (http.status_code)
- Время обработки (duration_ms)
- Идентификатор пользователя/партнёра (user.id, api_key_id)

**Бизнес-операции с заказом:**
- Идентификатор заказа (order.id)
- Идентификатор клиента (customer.id)
- Текущий статус заказа (order.status)
- Тип операции (operation: status_change, order_create, price_calculate, file_upload)
- Результат операции (result: success, failure)
- Источник запроса (source: b2c_website, b2b_api)

**Операции с очередью RabbitMQ:**
- Имя очереди (queue.name)
- Тип операции (messaging.operation: publish, consume)
- Идентификатор сообщения (message.id)
- Идентификатор заказа в сообщении (order.id)
- Размер сообщения (message.size_bytes)
- Результат (result: acknowledged, failed, requeued, dead_lettered)

**Операции с базой данных:**
- Тип операции (db.operation: insert, update, select, delete)
- Имя таблицы (db.table)
- Идентификатор заказа (order.id, если применимо)
- Время выполнения запроса (db.duration_ms)
- Количество затронутых строк (db.rows_affected)

**Операции с S3-хранилищем:**
- Тип операции (s3.operation: upload, download, delete)
- Имя бакета (s3.bucket)
- Имя файла (только имя, без пути) (file.name)
- Формат файла (file.format)
- Размер файла (file.size_bytes)
- Время выполнения (s3.duration_ms)

#### Специфичные логи для MES API

**Расчёт стоимости:**
- Время начала расчёта (calculation.start_time)
- Время завершения расчёта (calculation.end_time)
- Длительность расчёта (calculation.duration_ms)
- Количество полигонов в модели (model.polygon_count)
- Сложность модели (model.complexity: low, medium, high)
- Результат: стоимость (calculation.price) или ошибка (calculation.error)

#### Специфичные логи для CRM API

**Подтверждение заказа:**
- Идентификатор продавца (seller.id)
- Время подтверждения (approval.timestamp)
- Комментарий продавца (если есть) (approval.comment)

#### Специфичные логи для Shop API

**Загрузка файла 3D-модели:**
- Способ создания (file.source: uploaded, constructor)
- Идентификатор модели из конструктора (constructor.model_id)
- Контрольная сумма файла (file.checksum_sha256)

## Предлагаемое решение

### Технологический стек

| Компонент | Технология | Обоснование |
| :--- | :--- | :--- |
| Формат логов | Структурированный JSON | Машинная обработка, индексация полей, совместимость с любым коллектором |
| Библиотека логирования Java | Logback + logstash-logback-encoder | Стандарт для Spring Boot, нативный JSON-формат, поддержка MDC для контекста |
| Библиотека логирования C# | Serilog + Serilog.Formatting.Compact | Стандарт для .NET, структурированное логирование, обогащение контекстом |
| Коллектор логов | Vector (альтернатива: Fluent Bit) | Лёгкий, написан на Rust, низкое потребление ресурсов, нативная поддержка Kafka/OpenSearch |
| Буфер/брокер логов | Apache Kafka | Гарантированная доставка, переживает пиковые нагрузки, отделяет сбор от хранения |
| Хранилище и поиск | OpenSearch | Apache 2.0 лицензия, форк Elasticsearch, совместимость с Elasticsearch API |
| Визуализация | OpenSearch Dashboards | Совместимость с Kibana API, дашборды, поиск, алертинг |
| Оркестрация | Существующие EC2 + Yandex Managed Service for Kafka (или self-hosted) | Минимизация новых зависимостей |

### Как это работает

**Шаг 1. Генерация логов в приложении:**
Приложение пишет структурированные JSON-логи в stdout (рекомендация 12-factor app) или в файл. Каждая запись содержит обязательные поля: timestamp, level, service.name, trace.id, order.id (если применимо), message.

**Шаг 2. Сбор логов:**
Vector (или Fluent Bit) работает как sidecar-контейнер или агент на каждом EC2-инстансе. Читает логи из stdout/файлов, обогащает метаданными инстанса (имя хоста, окружение) и отправляет в Kafka.

**Шаг 3. Буферизация:**
Kafka принимает логи в виде топиков (logs.shop-api, logs.crm-api, logs.mes-api). Это обеспечивает:
- Буферизацию при пиковых нагрузках.
- Возможность перечитать логи при сбое хранилища.
- Независимость производительности приложений от скорости записи в хранилище.

**Шаг 4. Индексация:**
OpenSearch consumer читает из Kafka и индексирует логи в индексы с ротацией по дням (logs-shop-api-2026.05.30).

**Шаг 5. Поиск и анализ:**
OpenSearch Dashboards предоставляет интерфейс для:
- Полнотекстового поиска по логам.
- Фильтрации по полям (order.id, status, level).
- Построения дашбордов (количество ошибок по сервисам, распределение статусов заказов).

## Политика безопасности в отношении логов

### Чувствительные данные

Следующие данные не должны попадать в логи ни при каких обстоятельствах:
- Пароли, токены аутентификации, API-ключи (полное значение)
- Номера кредитных карт, платёжная информация
- Персональные данные клиентов (email, телефон, адрес) без хеширования

**Меры:**
- Настройка маскирования в Serilog/Logback: автоматическая замена паттернов (email → ***@***.***, phone → +7***)
- API-ключи: логировать только api_key_id и последние 4 символа ключа (api_key_suffix: "a1b2")
- Регулярный аудит логов на наличие чувствительных данных (автоматический скрипт)
- Процессор в Vector для удаления/маскирования полей до отправки в Kafka

### Контроль доступа

| Роль | Уровень доступа | Обоснование |
| :--- | :--- | :--- |
| Поддержка (L1) | Чтение логов INFO, поиск по order.id, customer.id | Достаточно для расследования типовых инцидентов |
| Разработчики | Чтение всех уровней, включая DEBUG (на dev) и ERROR/WARN (на prod) | Необходимо для отладки, но без персональных данных |
| DevOps | Чтение всех логов + доступ к инфраструктурным логам (Kafka, OpenSearch) | Обслуживание системы логирования |
| Администраторы | Полный доступ, включая управление retention и политиками безопасности | Управление системой |
| B2B-партнёры | Только логи своих запросов через API (ограниченный доступ) | Прозрачность обработки |

**Технические меры:**
- Аутентификация в OpenSearch Dashboards через корпоративный SSO (LDAP/OAuth2)
- Ролевая модель доступа (RBAC) на уровне OpenSearch
- Аудит-лог всех запросов к логам: кто, когда, какой запрос выполнил
- Изоляция dev-логов от prod-логов (разные индексы/кластеры)

## Политика хранения логов

### Стратегия индексов

| Окружение | Тип индекса | Retention | Размер (оценка) | Обоснование |
| :--- | :--- | :--- | :--- | :--- |
| dev | logs-dev-{service}-{date} | 7 дней | ~5 GB | Только для отладки, короткий цикл разработки |
| prod | logs-prod-{service}-{date} | 30 дней (hot) + 90 дней (cold) | ~50 GB hot + ~150 GB cold | 30 дней для оперативного расследования, 90 дней для трендов и SLA |
| prod (аудит) | audit-logs-prod-{date} | 1 год | ~100 GB | Юридическая значимость, доказательство обработки заказов |

### Ротация и управление жизненным циклом

- **Hot phase (0-30 дней):** Данные в OpenSearch, быстрое хранилище (SSD), полная доступность для поиска.
- **Cold phase (30-90 дней):** Данные переносятся в S3-совместимое хранилище (Yandex Object Storage), доступны только для восстановления.
- **Delete phase (90+ дней):** Автоматическое удаление согласно retention policy.
- **Аудит-логи:** Хранятся в отдельном индексе с годовым retention, cold phase после 30 дней.

### Ограничения размера

- Максимальный размер одной записи лога: 10 KB (ограничение на уровне приложения)
- Максимальный размер индекса в день: 50 GB (триггер алерта при приближении)
- Общий объём хранилища логов: 500 GB (мониторится, алерт при > 80%)

## Превращение системы сбора логов в систему анализа

### Алертинг на основе логов

Настройка алертов в OpenSearch Alerting:

| Алерт | Условие | Каналы уведомления | Действие |
| :--- | :--- | :--- | :--- |
| Всплеск ошибок ERROR | > 10 ERROR за 1 минуту в любом сервисе | Slack #on-call, звонок при > 50 | Автоматический сбор дампа состояния сервиса |
| Заказ завис в статусе | Нет INFO о смене статуса для order.id дольше N минут (N зависит от статуса) | Slack #support | Автоматическое создание тикета с деталями заказа |
| Сообщение в DLX | Лог уровня WARN с messaging.operation: dead_lettered | Slack #support, звонок при массовом (>10) | Немедленное расследование |
| Ошибка соединения с БД/S3/RabbitMQ | Лог уровня ERROR с db.operation: failed или s3.operation: failed | Slack #on-call, звонок | Автоматическая проверка доступности сервиса |
| Аномальный рост количества заказов | > 1000 заказов за 1 минуту (норма: ~10) | Slack #security | Проверка на DDoS/фрод |

### Поиск аномалий

1. **DDoS-атака или фрод:**
   - Метрика: rate(order_create) per minute
   - Аномалия: Среднее значение — 10 заказов/мин. Всплеск до 1000 заказов/мин.
   - Реакция: Автоматический алерт в #security, проверка source IP, временная блокировка подозрительных IP на уровне балансировщика.

2. **Деградация производительности расчёта стоимости:**
   - Метрика: avg(calculation.duration_ms) за 5 минут
   - Аномалия: Среднее время расчёта выросло с 3 минут до 15 минут.
   - Реакция: Алерт в Slack #development, проверка загрузки CPU worker'ов, анализ сложности поступающих моделей.

3. **Потеря сообщений в очереди:**
   - Метрика: count(dead_lettered_messages) за час
   - Аномалия: Обычно 0. Любое значение > 0 — аномалия.
   - Реакция: Немедленный алерт, автоматическое извлечение сообщения из DLX для анализа.

4. **Аномалия распределения статусов:**
   - Метрика: count(order) by status
   - Аномалия: Количество заказов в статусе SUBMITTED растёт, а в PRICE_CALCULATED — нет.
   - Реакция: Алерт о возможной проблеме с модулем расчёта стоимости.

## Дополнительное задание: Критерии выбора технологии для работы с логами

### Сравнительный анализ

| Критерий | ELK (Elasticsearch + Logstash + Kibana) | OpenSearch | Splunk | Loki + Grafana |
| :--- | :--- | :--- | :--- | :--- |
| Лицензия | Elastic License 2.0 (ограничения на SaaS) | Apache License 2.0 (полностью открытая) | Проприетарная (дорогая) | AGPLv3 (открытая) |
| Модель данных | Полнотекстовый поиск, агрегации | Полнотекстовый поиск, агрегации (форк ES 7.10) | Полнотекстовый поиск, ML-аналитика | Только индексация метаданных, поиск по логам через grep |
| Масштабируемость | Высокая (кластеризация, шардирование) | Высокая (аналогично ES) | Высокая (корпоративный уровень) | Высокая (разделение чтения/записи) |
| Требования к ресурсам | Высокие (Java heap, SSD) | Высокие (аналогично ES) | Очень высокие | Низкие (не индексирует тело лога) |
| Сложность эксплуатации | Высокая (настройка JVM, шардов) | Средняя (упрощённое управление) | Низкая (управляется вендором) | Низкая |
| Интеграция с Kafka | Нативная (Logstash/Beats) | Нативная (Data Prepper) | Нативная (Universal Forwarder) | Через Promtail |

### Выбор для «Александрита»: OpenSearch

**Обоснование на основе критериев:**

1. **Лицензия (критично):**
   - Elasticsearch перешёл на несвободную лицензию, что создаёт риски для компании, предоставляющей API партнёрам (формально это SaaS).
   - OpenSearch — полностью открытая лицензия Apache 2.0, никаких ограничений.

2. **Совместимость (важно):**
   - OpenSearch является форком Elasticsearch 7.10. Все существующие клиенты, библиотеки и дашборды совместимы.
   - Переход с ELK на OpenSearch минимально болезненный в будущем.

3. **Стоимость (важно для растущего бизнеса):**
   - Self-hosted OpenSearch бесплатен. При текущих объёмах (~50 ГБ логов/день) Splunk стоил бы $7,500/месяц.
   - Компания уже использует Yandex Cloud — OpenSearch можно развернуть на Managed Service for OpenSearch или на своих EC2.

4. **Функциональность (важно):**
   - Полнотекстовый поиск по логам — основное требование. OpenSearch предоставляет его полностью.
   - Алертинг встроен и бесплатен (в отличие от базовой лицензии Elastic).
   - SQL-интерфейс для аналитиков, не знакомых с DSL запросами.

5. **Экосистема (дополнительный плюс):**
   - Data Prepper (замена Logstash) нативно работает с OpenSearch и Kafka.
   - OpenSearch Dashboards (форк Kibana) предоставляет идентичный интерфейс.

**Почему не другие варианты:**
- **ELK:** Риски лицензии (Elastic License 2.0) для B2B-сервиса, ограничения на SaaS-использование.
- **Splunk:** Неоправданно дорого для объёмов «Александрита». Стоимость будет расти линейно с ростом заказов.
- **Loki:** Не подходит, так как не индексирует тело логов — только метаданные. Полнотекстовый поиск по сообщениям об ошибках и деталям заказа будет медленным или невозможным. Основное требование «Александрита» — быстрый поиск по содержимому логов (текст ошибки, идентификаторы).
