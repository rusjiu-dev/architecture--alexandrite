# Проект внедрения кеширования для системы «Александрит»

---

## Мотивация

### Почему необходимо внедрить кеширование

Текущая ситуация в системе характеризуется двумя симптомами, указывающими на необходимость кеширования:

**Проблема 1: Низкая скорость работы дашборда MES**
Операторы жалуются на долгую загрузку первой страницы MES, где отображается список заказов в работе с фильтром по статусам. Пагинация и фильтрация, реализованные командой, проблему не решили. Корневая причина — каждый запрос к странице порождает тяжёлый SQL-запрос к базе данных MES, которая одновременно обслуживает операции расчёта стоимости и записи статусов. Кеширование результатов наиболее частых запросов снизит нагрузку на БД и ускорит отклик интерфейса.

**Проблема 2: Медленное выполнение заказов (косвенный эффект)**
Новые клиенты недовольны скоростью выполнения заказа. Хотя это комплексная проблема, часть задержки связана с тем, что операторы не могут быстро увидеть новые заказы и взять их в работу. Ускорение дашборда напрямую сокращает время реакции оператора на новый заказ.

**Элементы, предлагаемые к кешированию:**

| Компонент | Данные для кеширования | Обоснование |
|---|---|---|
| MES API | Список заказов для дашборда (сгруппированный по статусам, с пагинацией) | Наиболее частый и тяжёлый запрос, вызывающий жалобы |
| MES API | Список новых заказов (статусы SUBMITTED, PRICE_CALCULATED) | Операторам критично быстро видеть новые заказы для получения вознаграждения |
| MES API | Данные конкретного заказа (детальная страница) | Второй по частоте запрос после списка |

**Что не кешируется на данном этапе:**
- Результаты расчёта стоимости — каждый расчёт уникален, кеширование не даст выгоды.
- Shop API и CRM API — жалобы сконцентрированы на MES, кеширование в других сервисах преждевременно.

---

## Предлагаемое решение

### Тип кеширования: серверное

**Обоснование:**
- Клиентское кеширование (в браузере) не решает проблему, так как разные операторы работают с разных устройств, а данные должны быть консистентными между всеми пользователями.
- Серверное кеширование размещается между MES API и MES DB, обслуживая всех операторов.
- Кеш находится близко к приложению (In-Memory или внешний Redis), что обеспечивает минимальную латентность.

### Паттерн кеширования: Cache-Aside (Lazy Loading)

**Обоснование выбора:**

Cache-Aside выбран как оптимальный паттерн для сценария дашборда MES по следующим причинам:

1. **Толерантность к отказам кеша:** Если Redis недоступен, приложение продолжает работать, обращаясь напрямую к PostgreSQL. Дашборд замедлится, но не откажет полностью.

2. **Ленивая загрузка:** Кешируются только реально запрашиваемые данные. Нет смысла прогревать кеш для всех возможных комбинаций фильтров, если 80% запросов — это «новые заказы» и «заказы в работе».

3. **Простота реализации:** Приложение управляет кешем явно. Нет необходимости в сложной синхронизации между кешем и БД.

4. **Гибкость инвалидации:** Приложение само решает, когда инвалидировать данные, что позволяет реализовать инвалидацию по бизнес-событиям.

**Почему не другие паттерны:**

| Паттерн | Причина отказа |
|---|---|
| **Write-Through** | Каждое изменение статуса заказа должно синхронно записываться и в БД, и в кеш. Удваивает время записи. Для MES, где важна скорость реакции, это неприемлемо. Кроме того, список заказов — составная структура, а не одна запись. Write-Through для списков требует перестроения всего списка при каждом изменении. |
| **Write-Behind** | Запись сначала в кеш, потом асинхронно в БД. Риск потери данных при сбое кеша до синхронизации. Для статусов заказа это недопустимо — потеря перехода статуса приведёт к зависшему заказу. |
| **Refresh-Ahead** | Требует предсказания, какие данные понадобятся в будущем. Для дашборда с произвольными фильтрами предсказать невозможно. Избыточно сложен для текущей задачи. |

### Стратегия инвалидации кеша

Выбрана **комбинированная стратегия: инвалидация по бизнес-ключу + временная инвалидация (TTL)**.

#### Основная стратегия: инвалидация по бизнес-ключу (программная)

**Описание:** При изменении статуса заказа приложение явно удаляет из кеша все затронутые записи, используя паттерны ключей.

**Ключи кеша и их инвалидация:**

| Кешируемые данные | Ключ | Инвалидация при изменении заказа |
|---|---|---|
| Список заказов по статусу (страница) | `dashboard:orders:status:{status}:page:{page}` | `DEL dashboard:orders:status:{old_status}:*` и `DEL dashboard:orders:status:{new_status}:*` |
| Детальная информация о заказе | `order:detail:{order_id}` | `DEL order:detail:{order_id}` |
| Счётчик заказов по статусам | `dashboard:counters` | `DEL dashboard:counters` |

**Почему подходит:**
- Инвалидация происходит немедленно после изменения, что гарантирует консистентность данных.
- Операторы видят актуальный список сразу после изменения статуса.
- Использование паттернов (`*`) позволяет удалить все страницы пагинации для статуса одной операцией.

#### Дополнительная стратегия: временная инвалидация (TTL)

**Описание:** Каждая запись в кеше имеет время жизни (TTL) — 30 секунд для списков, 60 секунд для деталей заказа.

**Почему нужна дополнительно:**
- Защита от «забытых» ключей: если инвалидация по ключу не сработала (ошибка, новое поле статуса), TTL гарантирует, что устаревшие данные будут удалены.
- Автоматическая очистка кеша от редко запрашиваемых страниц пагинации.
- Простота: не требует сложной логики отслеживания всех возможных событий.

**Почему не другие стратегии:**

| Стратегия | Причина отказа |
|---|---|
| **Только TTL** | Задержка до 30 секунд между изменением статуса и обновлением дашборда неприемлема для операторов, чьё вознаграждение зависит от скорости реакции. |
| **Полный сброс кеша** | Удаление всего кеша при любом изменении приведёт к лавине запросов к БД и деградации производительности. |
| **Write-Through инвалидация** | Требует обновления составных списков в кеше при каждом изменении, что дорого и сложно (нужно перестраивать список). |
| **Отложенная инвалидация** | Создаёт окно неконсистентности, когда разные операторы видят разные данные. |

### Итоговая стратегия

```
Инвалидация = программная (по ключу) + временная (TTL)
```

- При изменении статуса: немедленное удаление всех связанных ключей.
- Фоновый механизм: TTL 30 секунд для списков, 60 секунд для деталей.
- В случае сбоя инвалидации: TTL страхует от «вечно устаревших» данных.

## Дополнительное задание: Сравнительный анализ вариантов архитектуры кеширования

### Вариант 1: Встроенный In-Memory Cache (MemoryCache в C#)

**Описание:** Кеш размещается в памяти процесса MES API. Не требует внешних зависимостей. Данные кешируются в словаре с TTL.

**Плюсы:**
- Минимальная латентность (доступ к памяти < 1 мс)
- Нулевые затраты на инфраструктуру (нет отдельного сервера)
- Простота реализации (встроен в ASP.NET Core)
- Нет сетевых вызовов, нет сериализации/десериализации

**Минусы:**
- Кеш не разделяется между инстансами MES API (после масштабирования до 2+ инстансов — дублирование данных)
- При рестарте приложения кеш теряется полностью (холодный старт)
- Потребляет оперативную память приложения (конкурирует с бизнес-логикой)
- Инвалидация по ключу с паттернами (`*`) ограничена или требует собственной реализации
- Размер кеша ограничен памятью одного инстанса

### Вариант 2: Внешний распределённый кеш (Redis)

**Описание:** Кеш размещается в отдельном инстансе Redis (или кластере). Все инстансы MES API обращаются к одному Redis.

**Плюсы:**
- Общий кеш для всех инстансов MES API (консистентность после масштабирования)
- Сохранность кеша при рестарте приложений (тёплый старт)
- Нативная поддержка паттернов ключей (`DEL dashboard:orders:status:*`)
- Не потребляет память приложения
- Возможность масштабирования Redis независимо от приложения (Redis Cluster)
- Дополнительные структуры данных (Sorted Sets для сортировки заказов по времени)

**Минусы:**
- Сетевая латентность (~1-5 мс против < 1 мс для In-Memory)
- Дополнительный инстанс для обслуживания (стоимость, мониторинг)
- Сериализация/десериализация данных (нагрузка на CPU)
- Единая точка отказа (требуется Redis Sentinel или Cluster для HA)
- Сложнее в отладке (сетевые таймауты, проблемы с соединением)


### Сравнительная таблица вариантов

| Критерий | Вариант 1: In-Memory Cache | Вариант 2: Redis |
|---|---|---|
| **Латентность** | < 1 мс (лучше) | 1-5 мс |
| **Масштабируемость** | Не масштабируется (каждый инстанс — свой кеш) | Масштабируется (общий кеш) |
| **Инвалидация по паттерну** | Ограничена, требует реализации | Нативная команда DEL с паттернами (лучше) |
| **Сохранность при рестарте** | Теряется полностью | Сохраняется |
| **Инфраструктурные затраты** | Отсутствуют | Требуется Redis-инстанс |
| **Потребление памяти приложения** | Увеличивает потребление | Не влияет |
| **Отказоустойчивость** | Нет дополнительной точки отказа | Требует Redis HA (Sentinel/Cluster) |
| **Поддержка структур данных** | Key-Value только | Sorted Sets, Lists, Hashes (полезно для сортировки) |
| **Подходит для текущей архитектуры** | Да (1 инстанс MES API) | Да (подготовка к масштабированию) |
| **Подходит для целевой архитектуры** | Нет (после масштабирования — дубли и неконсистентность) | Да (общий кеш для N инстансов) |

### Заключение

**Рекомендованный вариант: Redis (Вариант 2)**

Обоснование:

1. **Стратегическое соответствие целевой архитектуре.** В рамках инициативы «Обеспечение базовой отказоустойчивости и масштабируемости» (приоритет 3 из первого ответа) планируется увеличение количества инстансов MES API до 2+ с балансировщиком. In-Memory Cache в такой конфигурации приведёт к рассинхронизации: оператор, попавший на инстанс A, увидит устаревшие данные после того, как оператор на инстансе B изменил статус заказа. Redis решает эту проблему изначально.

2. **Нативная инвалидация по паттернам.** Redis поддерживает команду `DEL dashboard:orders:status:*`, что критично для инвалидации всех страниц пагинации при изменении статуса. Реализация того же в In-Memory Cache потребует написания и поддержки собственного кода.

3. **Приемлемая стоимость.** Redis-инстанс на Yandex Managed Service for Redis с минимальной конфигурацией стоит незначительно по сравнению с потерями от одного упущенного контракта. При этом закладывается фундамент для дальнейшего роста.

4. **Дополнительные возможности.** Sorted Sets в Redis могут быть использованы для эффективной сортировки заказов по времени создания (с использованием `ZADD` и `ZREVRANGE`), что полностью снимет нагрузку с PostgreSQL для этой операции.

**Почему не In-Memory:**
- Уже в ближайшие полгода потребуется масштабирование MES API, и In-Memory кеш придётся полностью переписывать на Redis.
- Риск неконсистентности данных между инстансами приведёт к новым жалобам операторов, что сведёт на нет эффект от ускорения дашборда.
