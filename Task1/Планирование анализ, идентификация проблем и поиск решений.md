# Планирование: анализ, идентификация проблем и поиск решений

## Анализ проблемных мест

На основе схемы и описания идентифицированы следующие существующие и потенциальные проблемы:

1.  **Неэффективный процесс ручного E2E-тестирования перед релизом.**
    - **Симптом:** Ручное E2E-тестирование на релизном окружении — узкое место. Блокирующие баги (high/highest), найденные в конце спринта, вызывают задержки релиза до месяца и более.
    - **Коренная причина:** Отсутствие автоматизированных регрессионных тестов и практики раннего тестирования. Качество версии проверяется в самый последний момент.

2.  **Длительная и ресурсоёмкая операция расчёта стоимости заказа, не рассчитанная на высокие нагрузки.**
    - **Симптом:** Расчёт стоимости занимает от 2 до 30 минут. После открытия API, MES-сервис, отвечающий за это, оказался перегружен потоком внешних запросов.
    - **Коренная причина:** Тяжёлая вычислительная операция выполняется синхронно в рамках обработки API-запроса, блокируя ресурсы веб-сервера и создавая очередь, что приводит к деградации всего MES-приложения.

3.  **Проблемы с производительностью дашборда MES.**
    - **Симптом:** Первая страница MES со списком заказов долго загружается у операторов. Пагинация и фильтрация проблему не решили. Операторам критично быстро видеть новые заказы, так как от этого зависит их вознаграждение.
    - **Коренная причина:** Вероятно, неоптимальные запросы к базе данных, отсутствие эффективного индексирования или кэширования. Запросы на получение списка заказов могут конкурировать за ресурсы БД с процессом расчёта стоимости, усугубляя проблему.

4.  **Отсутствие отказоустойчивости и проблемы с масштабированием.**
    - **Симптом:** Каждое приложение и база данных развёрнуты в единственном инстансе. Это создаёт единую точку отказа.
    - **Коренная причина:** Архитектура не предусматривает горизонтального масштабирования. Растущая линейно нагрузка (100+ заказов в месяц + API-трафик) рано или поздно упрётся в потолок производительности одного сервера и одной БД.

5.  **Блокирующая зависимость между онлай-магазином и MES при расчёте стоимости.**
    - **Потенциальная проблема:** Сценарий расчёта стоимости, инициируемый пользователем из онлайн-магазина (статус SUBMITTED -> PRICE_CALCULATED), вероятно, реализован через синхронный вызов. Это делает магазин чувствительным к недоступности или медленной работе MES.

6.  **Ручной и рискованный процесс деплоя на продуктив.**
    - **Симптом:** Релизы деплоятся вручную. Это медленно, подвержено человеческим ошибкам и не позволяет быстро откатить изменения в случае проблем.
    - **Коренная причина:** CI/CD пайплайн не автоматизирован до конца для всех окружений.

7.  **Разрозненность данных о заказе между системами.**
    - **Потенциальная проблема:** Статусы заказа распределены между Shop, MES и CRM, а обмен идёт через RabbitMQ. Это усложняет получение консистентного и актуального состояния заказа для поддержки и аналитики, а также может приводить к рассинхронизации.

8.  **Технологический зоопарк и риски "bus factor".**
    - **Симптом:** В команде по одному разработчику на ключевые технологии (один C# разработчик на MES, один React-разработчик). DevOps-инженер всего один.
    - **Коренная причина:** Нехватка экспертизы и взаимозаменяемости создаёт риски простоя при уходе или болезни ключевых сотрудников.

## Список инициатив в порядке приоритета

Приоритеты расставлены на основе влияния на бизнес-метрики (потеря контрактов, жалобы клиентов и операторов) и технической срочности.

### 1. [Срочное] Оптимизация расчёта стоимости и MES API

**Описание:** Немедленно вывести тяжёлую операцию расчёта стоимости из синхронного цикла обработки API-запроса.

**Действия:**
- Перевести обработку запросов на расчёт стоимости (как из онлай-магазина, так и по внешнему API) на асинхронную модель с использованием очереди (например, отдельная очередь в RabbitMQ).
- Создать отдельный сервис-воркер (background worker) на C# для выполнения расчётов, который будет читать задачи из очереди, выполнять их и сохранять результат.
- Внешний API и внутренний вызов из Shop API немедленно возвращают `202 Accepted` с идентификатором задачи.
- Реализовать endpoint для проверки статуса и получения результата расчёта.

### 2. [Срочное] Решение проблем с производительностью дашборда MES

**Описание:** Устранить долгую загрузку главной страницы для операторов, чтобы исключить жалобы и простой.

**Действия:**
- Провести профилирование запросов к БД MES, вызываемых дашбордом.
- Добавить необходимые индексы в таблицы БД MES (MES db).
- Реализовать кэширование (In-Memory Cache, Redis) для списка новых заказов по статусам.
- Рассмотреть возможность подписки на события (через очередь) для мгновенного обновления UI оператора (WebSockets), чтобы убрать необходимость частого полного обновления страницы.

### 3. [Краткосрочное] Обеспечение базовой отказоустойчивости и масштабируемости

**Описание:** Устранить единые точки отказа для критичных к нагрузке компонентов.

**Действия:**
- Увеличить количество инстансов для MES API и Shop API минимум до двух, разместив их за балансировщиком нагрузки.
- Настроить автомасштабирование для этих групп серверов на основе метрик CPU/RAM.
- Перевести базы данных (хотя бы MES db и Shop DB) в режим "только чтение" с репликой, настроив чтение с реплики для неблокирующих операций.

### 4. [Среднесрочное] Внедрение автоматизированного E2E-тестирования и изменение процесса

**Описание:** Убрать блокирующее ручное тестирование с критического пути релиза.

**Действия:**
- Выделить ключевые бизнес-сценарии (оформление заказа, расчёт стоимости, передача в производство).
- Покрыть эти сценарии автотестами (Selenium, Cypress, Playwright), интегрированными в CI/CD пайплайн.
- Запускать автотесты на dev-окружении после каждого мёржа PR.
- Изменить процесс: ручное тестирование на релизном окружении становится исследовательским и подтверждающим, а не единственным фильтром.

### 5. [Среднесрочное] Автоматизация деплоя на все окружения

**Описание:** Ускорить и обезопасить процесс доставки изменений до продакшена.

**Действия:**
- Реализовать полную автоматизацию деплоя на release и prod окружения в CI/CD (GitLab CI, GitHub Actions).
- Внедрить стратегию деплоя "Blue-Green" или "Rolling Update" для возможности мгновенного отката.
- Автоматизировать процесс отката на предыдущую стабильную версию.

### 6. [Среднесрочное] Усиление команды для снижения технологических рисков

**Описание:** Устранить зависимость от единственных носителей экспертизы.

**Действия:**
- Нанять второго разработчика C# (с фокусом на бэкенд) в качестве приоритета.
- Нанять или обучить второго DevOps-инженера.
- Поощрять кросс-функциональное взаимодействие и парное программирование между Java и C# разработчиками.

### 7. [Долгосрочное] Оптимизация потоков данных и консистентности заказов

**Описание:** Упростить и сделать надёжным обмен данными между системами.

**Действия:**
- Провести аудит сообщений в RabbitMQ и состояний заказов.
- Внедрить паттерн "Transactional Outbox" для гарантированной отправки сообщений при изменении состояния заказа.
- Рассмотреть создание выделенного сервиса управления заказами (Order Service), который будет единым источником истины для статусов заказа, к которому будут обращаться все остальные системы.

## Целевая архитектура через полгода

Через полгода архитектура будет эволюционировавшим вариантом текущей, сфокусированным на стабильности, производительности и управляемом росте.

**Уровень приложений:**
- Shop API и MES API работают в режиме отказоустойчивого кластера (минимум 2 инстанса) с автомасштабированием.
- Из MES API выделен независимый Calculation Worker (C# Background Service), который масштабируется отдельно и обрабатывает задачи расчёта стоимости из очереди RabbitMQ.
- MES SPA (React) для дашборда операторов использует WebSocket-соединение с BFF (Backend For Frontend) для мгновенного получения обновлений о новых заказах.

**Уровень данных:**
- Основные БД (Shop DB, MES db) имеют хотя бы одну реплику для чтения, что позволяет разгрузить мастер.
- Внедрён кэш Redis для часто запрашиваемых данных (дашборд MES, каталог магазина).

**Интеграции:**
- Расчёт стоимости полностью асинхронен.
- Взаимодействие между сервисами по ключевым сценариям (создание заказа через API) обеспечивается гарантированной доставкой сообщений.

**Процессы:**
- CI/CD полностью автоматизирован для всех окружений.
- Критические E2E-сценарии покрыты автотестами и являются частью пайплайна, что позволяет выпускать релизы стабильно раз в две недели.

## Три инициативы на ближайшие полгода (при ограничении)

Если есть возможность выполнить только три пункта, выбор падёт на те, которые максимально быстро устранят самые болезненные бизнес-проблемы и предотвратят немедленный коллапс:

1.  **Оптимизация расчёта стоимости и MES API (Инициатива №1).**
    - **Почему:** Это прямая и главная причина потери B2B-контрактов и роста жалоб. Асинхронная обработка немедленно разгрузит MES, сделав API стабильным и предсказуемым, что критически важно для партнёров.

2.  **Решение проблем с производительностью дашборда MES (Инициатива №2).**
    - **Почему:** Это напрямую влияет на операционную эффективность и мотивацию операторов. Если операторы не могут быстро брать заказы в работу, производство простаивает, а проблема просроченных заказов усугубляется, несмотря на наличие мощностей.

3.  **Обеспечение базовой отказоустойчивости и масштабируемости (Инициатива №3).**
    - **Почему:** Это фундамент для всего. Решение первых двух проблем без возможности масштабирования даст лишь временный эффект. С ростом нагрузки на 100+ заказов в месяц и новым API, единственный инстанс станет узким местом очень быстро. Горизонтальное масштабирование и репликация БД — обязательное условие для выживания системы под новой нагрузкой.
